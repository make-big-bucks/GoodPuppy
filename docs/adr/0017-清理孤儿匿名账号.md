# ADR-0017：定时清理孤儿匿名账号

- 状态：已采纳
- 日期：2026-06-21
- 关联：[ADR-0002](0002-supabase-匿名登录身份方案.md)（匿名登录身份方案）

## 背景

匿名「快速进入」（`supabase.auth.signInAnonymously()`）会在 `auth.users` 创建一个真实用户（`is_anonymous = true`），session 通过 `persistSession` 持久化在客户端 localStorage。

未绑定邮箱的匿名账号有一个致命特性：它**没有任何可重新登录的凭据**。一旦用户退出登录（`signOut()` 清掉本地 token）或长期不再使用导致 token 失效，就再也无法登回那个 `auth.uid()`。该账号及其在服务器上的数据（`profiles`、`messages`、`room_members` 等）随即变成**不可达的僵尸数据**：

- 永久占用 `auth.users` 与各业务表，缓慢膨胀数据库与 Auth 用户数统计。
- 匿名入口容易被刷出大量空账号，放大上述问题。
- 用户主动退出后仍把其数据留存，不符合「退出即清理」的隐私预期。

ADR-0002 已记录「匿名账号退出后无法找回」这一负面后果，但未规定服务器侧这些孤儿数据如何处理。

## 决策

新增服务端定时清理，**只删除真正不可达的孤儿匿名账号，保留其产生的内容并匿名化**。

### 1. 删除判定：只看「有没有 session」，不看活跃时间

清理函数 `public.cleanup_orphaned_anonymous_users(p_grace_days integer DEFAULT 1)`（`SECURITY DEFINER`）删除满足全部条件的账号：

- `is_anonymous = true`
- `created_at` 早于 `now() - p_grace_days`（新账号宽限期，默认 1 天）
- 在 `auth.sessions` 中**没有任何 session**（`NOT EXISTS`）

之所以不以"最近 N 天是否活跃"作为判定（早期设计曾用 `auth.sessions.updated_at` 的近期性），是因为它会**误删只是长期没开 app、但从未退出登录的用户**：电脑关机两周回来,账号连同宠物、房间、聊天就没了——这与 GoodPuppy 靠"在场感/留存"立命的产品定位（ADR-0002）直接冲突。

改为只删「零 session」的账号后：

- 退出登录(supabase-js `signOut()` 默认 global scope)会删除服务器端 session 行 → 零 session → 宽限期后清理。
- **仍持有 session 的休眠匿名账号永不清理**。Supabase 默认不设刷新令牌失活超时,休眠 session 会一直存在。

`auth.users.last_sign_in_at` 不适合做活跃锚点:匿名账号它约等于 `created_at` 且不随 token 刷新更新。

宽限期取 **1 天**(只防误删刚创建、session 尚未落库的新账号),通过 `pg_cron` 每天 03:00 UTC 执行一次。函数对客户端角色 `REVOKE` 执行权限,仅供后台调用。

> 注意:若日后在 Supabase Auth 开启「refresh token inactivity timeout」,休眠 session 会被服务器回收,届时这些休眠账号会重新落入清理范围,需要时再权衡。

### 2. 级联策略：保留内容、匿名化

`profiles.id -> auth.users` 本就是 `ON DELETE CASCADE`，删账号会连带删 `profiles`，再级联清理 `presence` / `room_members`。但删账号前需要决定其留下的消息和房间如何处理。原先 `messages.sender_id` / `rooms.created_by` / `connection_requests.{from_id,to_id}` 均为 `NO ACTION` 且列 `NOT NULL`，会**阻断删除**。

选择「保留内容、匿名化」：

| 关联 | 调整后规则 | 理由 |
|------|-----------|------|
| `messages.sender_id` | `SET NULL`（列改可空） | 保留聊天历史，发送者匿名化 |
| `rooms.created_by` | `SET NULL`（列改可空） | 房间是共享资源，创建者退出不应连带删房 |
| `connection_requests.{from_id,to_id}` | `CASCADE` | 临时的加好友 / 入房请求，任一方消失即失去意义 |

`messages.sender_id` 之所以用 `SET NULL` 而非删除外键：前端聊天记录用 PostgREST 内嵌 `profiles!messages_sender_id_fkey` 解析发送者，依赖该外键存在，删约束会破坏查询。前端 `resolveSender()` 已兼容 `sender_id` 为 null 的情况，渲染为通用「已注销用户」。写入侧 RLS 仍强制 `sender_id = auth.uid()`，不会写入 null。

## 后果

**正面：**
- 退出登录(零 session)的孤儿匿名账号被定期清除，控制库膨胀与 Auth 用户数，贴近"退出即清理"的隐私预期。
- 共享的聊天记录与房间得以保留，对仍在使用的另一方无感。
- 只删零 session 账号，**长期休眠但未退出登录的用户绝不会被误删**(出差/假期回来账号仍在)。

**负面：**
- 账号被 `SET NULL` 清理后，该用户的多条历史消息会collapse 为同一个「已注销用户」，无法再按账号区分（区别于 profile 仅缺失但 `sender_id` 仍在的兜底场景，后者仍可按 uuid 末 4 位区分）。
- 引入 `pg_cron` 依赖与一个 `SECURITY DEFINER` 删除函数，需注意权限边界（已 REVOKE 客户端权限）。
- `messages.sender_id` / `rooms.created_by` 改为可空，前端与类型需处理 null（已完成）。

**调参：** 修改保留天数时改 cron 命令实参或重新 `cron.schedule` 同名任务（按 jobname 幂等覆盖）。
