# ADR-0008：分层动画状态机与实时事件总线

- 状态：已采纳（基础层成员与互动「单角色原则」已被 [ADR-0009](0009-互动双角色动画与-idle-变体.md) 演进；三层优先级模型与实时事件总线仍有效）
- 日期：2026-06-10

## 背景

早期原型用 `state_images/state_NN.gif` 加编号（`stateCount = 24`）渲染 pet，前端把一个整数当成「当前状态」，唯一入口是右键菜单循环切换编号。这套机制无法承载 `docs/桌宠动画清单.md` 描述的语义化动画与交互：

- 动画清单按**触发条件**组织（无操作待机、拖动、发消息、好友互动、进入/离开、情绪、工作状态），编号体系无法表达「哪个动画该在什么时候播」。
- 清单本身留下两个待解决问题：**动画优先级**，以及**情绪状态与工作状态是否并存**。
- 多个动画涉及跨用户互动（喂食、踢飞、贴贴、进出场打招呼，均标记「是否通信=是」），需要一条实时管线，但这类信号高频、瞬时、对持久化价值很低。
- 远端 pet 此前永远停在默认帧，没有任何动画驱动。

`skills/hatch-puppy-pet` 产出的资源已按清单制作为 15 个语义状态（带 `pet.json` 描述帧数/时长/loop），需要在代码层接入并保持可扩展。

## 决策

### 1. 三层优先级状态机（单一画面）

任一时刻只渲染一个状态，按层解算：**瞬时层 > 状态层 > 基础层**。

| 层 | 成员 | 行为 |
|---|---|---|
| 瞬时层 | drag-trot（按住型）、message、cuddle、feed、kicked、enter-run、greet、leave-thrown | 一次性播完自动清除；按住型在外部条件解除前持续 |
| 状态层 | happy / sad / busy / bored | **单槽互斥**：情绪与工作共用一个槽，后设的替换前者，`null` 即回落基础层 |
| 基础层 | idle / wander / sit-stand | 自主循环营造「鲜活」表现 |

把持续状态收敛成**单槽**而非情绪/工作两个独立维度，一次性回答了清单里「是否并存」的疑问，也让状态机最简。每只 pet（self 与每个 remote）持有一个 `PetAnimator` 实例，self 由本地输入与右键菜单驱动，remote 由实时层喂入。

### 2. 行为事实与资源事实分离

- `pet.json`（各 pet 目录下）只描述**资源事实**：帧数、每帧时长、loop。
- `src/windows/pet/animationCatalog.ts` 描述**行为事实**：状态属于哪层、是一次性/按住/持续、互动由谁播、形象注册表。

新增动画 = catalog 加一行 + 一个 GIF；新增互动 = `INTERACTIONS` 加一条路由；新增形象 = 一个 `public/pets/<id>/` 目录 + 注册表一行。

### 3. 实时事件总线（零建表）

- **持续状态 + 形象**：随 Supabase Realtime presence 的 track payload 携带 `status` 与 `pet_id`，随上下线/变更同步；远端据此设置对应 pet 的状态层与形象。
- **瞬时互动**：room 维度单独一条 broadcast channel，事件 `{ action, actorId, targetId }`，纯瞬时、不落库、不进消息历史。互动「由谁播」遵循单角色原则：踢飞/喂食由**目标**播、贴贴由**发起者**播。

两者都是 Supabase Realtime 的客户端能力，**不新增任何表**，契合 ADR-0004「前端 webview 承担业务逻辑」。刻意不复用 `messages.kind='emote'` 落库，避免污染文字消息历史并产生无谓写入。

## 后果

**正面：**

- 清单中所有「待制作」动画在代码层可触发，优先级与并存问题有确定答案。
- 可扩展骨架清晰，加动画/互动/形象都是局部一行级改动。
- 资源与行为解耦，`pet.json` 可由 skill 独立产出而不必了解 app 行为。
- 实时层零建表，远端 pet 能反映对方持续状态并播放互动动画。

**负面：**

- 「单一画面」意味着情绪与工作无法同时呈现；若未来要叠加需引入组合资源或多层渲染。
- broadcast 事件不持久化，离线/错过即丢失，不可回放——对桌宠互动可接受。
- 一次性动画的结束依赖客户端定时器（按 `pet.json` 时长），而非 GIF 播放完成事件。

**约束：**

- GIF 仍为单角色（被踢的 pet 播 kicked，踢的一方不播），配对/定位/时序由 app 负责。
- 远端 pet 形象依赖对方 presence payload 中的 `pet_id`，未知形象回退到默认。
