# ADR-0003：统一房间数据模型替代双用户双表设计

- 状态：已采纳
- 日期：2026-06-05

## 背景

当前原型使用硬编码的双用户、双表设计：

- `currentUser` 在编译时写死，靠 `build-mac-user-a.js` 为每人单独打包。
- 消息分 `user_a_message` / `user_b_message` 两张表，presence id 写死 1/2。
- 渲染层固定显示两只 pet，无法支持更多成员。

这一设计的本质缺陷在于：**用户系统和安全边界缺失**，无法支持真实的多用户场景。随着 Slice 2（运行时身份）的推进，需要从根本上重构数据模型。

同时，GoodPuppy 的核心单位是**房间（亲密小圈子）**——既覆盖 1:1，也覆盖小群，两者在产品层面没有本质区别，不应在数据层面人为割裂。

## 决策

采用以 `room` 为核心的统一关系数据模型，消灭所有硬编码的用户引用和双表结构。

核心表结构：

```
profiles        -- 用户身份（id = auth.uid()，gp_id 为对外短码）
rooms           -- 房间（含 invite_code，支持邀请码加入）
room_members    -- 房间成员关系（多对多）
connection_requests  -- 按 GoodPuppy ID 的连接请求流程
messages        -- 统一消息表（通过 room_id 隔离）
presence        -- 在线状态（通过 room_id + user_id 隔离）
```

进入房间的两种路径（并存，本质相同）：
1. **按个人 ID 连接**：B 输入 A 的 `gp_id` → 写 `connection_requests` → A 确认 → 自动建房间，双方加入 `room_members`。
2. **按邀请码加入**：分享房间的 `invite_code` → 对方输入即可加入。

## 后果

**正面：**
- 消灭 `user_a_message`/`user_b_message` 双表，消灭所有编译时硬编码用户引用。
- 1:1 和小群统一处理，多人对话是房间的自然结果，无需额外设计。
- RLS 可以统一基于 `room_id + auth.uid()` 做隔离，策略简洁。
- 两种进入房间的方式（按 ID / 按邀请码）在同一模型下自然共存。
- 为 Slice 3（连接流程）和 Slice 4（单窗口 presence 渲染，见 [ADR-0007](0007-单窗口-presence-渲染.md)）打好基础。

**负面：**
- 需要完整的数据库迁移，旧原型数据（双表）无法直接复用。
- `connection_requests` 引入了状态机（pending/accepted/declined），需要在 UI 层对应处理。

**约束：**
- `profiles.id` 与 `auth.uid()` 严格绑定，所有外键以此为准。
- `gp_id` 仅用于用户间查找，不作为任何鉴权依据。
- `invite_code` 需保证全局唯一（`unique` 约束），建议在应用层生成随机短码后入库。
