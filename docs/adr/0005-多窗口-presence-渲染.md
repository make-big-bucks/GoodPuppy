# ADR-0005：多窗口方案驱动 presence 渲染

- 状态：已采纳
- 日期：2026-06-05

## 背景

GoodPuppy 的核心价值主张是**环境式（ambient）在场感**——用户的好友"活在桌面上"，而不是藏在一个需要主动打开的应用窗口里。

当前原型固定渲染两只 pet（user_a / user_b）在同一窗口内，无法支持：
- 动态的成员上下线（pet 的到达与退场）。
- 多个房间成员同时在线（超过一个远程成员）。
- 每只 pet 独立的位置管理。

需要决定如何将 presence 状态映射为桌面上的视觉呈现。

**方案一：单窗口，canvas/DOM 内动态渲染多只 pet**
- 所有 pet 渲染在同一透明窗口内。
- 前端维护在线成员列表，动态增删 pet DOM 节点。

**方案二：多窗口，每只远程 pet 独立一个透明置顶窗口**
- 自己的 pet 常驻一个主窗口。
- 每个在线的远程成员对应一个独立的 Tauri 子窗口（透明、置顶、点击穿透）。
- Rust 主进程负责子窗口的生命周期（生成、定位、销毁）。

## 决策

采用**方案二**：多窗口方案，每只远程 pet 独立一个透明置顶窗口。

行为定义：
- **自己的 pet**：随应用启动常驻桌面，不受远程 presence 影响。
- **远程成员 pet**：成员上线时，Rust 侧生成一个新的透明子窗口，播放"到达动画"；成员离线时，播退场动画后销毁子窗口。
- **窗口定位**：Rust 侧管理各 pet 窗口的屏幕位置，避免重叠（具体布局策略在 Slice 4 的 spec 中细化）。

前端触发流程：
```
presence 订阅回调（成员上线）
  → 前端 invoke Tauri command "spawn_pet_window"（传入 user_id、pet_id）
  → Rust 创建透明子窗口，加载 pet renderer
  → 子窗口播放到达动画
```

## 后果

**正面：**
- 每只 pet 窗口完全独立——位置、动画、点击穿透均可独立控制，OS 层面天然隔离。
- "到达"/"离场"语义直接映射到窗口的创建/销毁，实现简单直观。
- 可以精细控制每只 pet 的 z-order 和点击穿透行为。
- 为将来支持"拖动 pet 到桌面任意位置"等交互留出空间。

**负面：**
- 多窗口带来更复杂的 Rust 窗口管理代码（需维护 window handle 映射）。
- 各子窗口与主窗口的通信需要通过 Tauri event 或 IPC，增加协调成本。
- 大量成员同时在线时，窗口数量线性增长，需要设定合理上限（v1 建议 ≤ 房间成员数，通常 2–6）。
- 子窗口的布局冲突（多只 pet 堆叠）需要额外的位置分配逻辑。

**约束：**
- v1 仅支持内置 pet（状态机风格，沿用 `state_images`），任意上传推迟到 v2。
- 到达动画和退场动画是 presence 体验的核心，不可缺失。
- 点击穿透必须在子窗口层面配置，确保 pet 不阻挡用户正常桌面操作。
