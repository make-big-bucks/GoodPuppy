# ADR-0007：单窗口方案驱动 presence 渲染

- 状态：已被取代（见 [ADR-0013：多窗口独立桌宠与协调者模型](0013-多窗口独立桌宠与协调者模型.md)）
- 日期：2026-06-06
- 取代：[ADR-0005：多窗口方案驱动 presence 渲染](0005-多窗口-presence-渲染.md)

## 背景

GoodPuppy 的核心体验仍然是环境式（ambient）在场感：用户和房间内在线成员的 pet 都应直接出现在桌面上，并且透明区域不应阻挡用户操作其他应用。

ADR-0005 曾选择多窗口方案：自己的 pet 常驻主窗口，每个在线远程成员生成一个独立透明置顶窗口。该方案在概念上能让每只 pet 拥有独立位置、动画和点击穿透状态，但在开发验证中暴露出 MVP 阶段不划算的复杂度：

- 动态窗口需要额外的 Tauri capability 覆盖，否则子窗口无法稳定调用拖动、定位和点击穿透相关 API。
- macOS 透明置顶窗口需要 `NSPanel`、Space、窗口层级和非激活面板等特殊处理；窗口数量增加会放大这些平台细节。
- 点击穿透和像素级命中测试本身已经复杂，多窗口会让每个窗口都维护一套状态机和原生光标坐标流。
- 原生拖动最稳定的方式是在 `pointerdown` 早期调用 `startDragging()`；多窗口下每个 pet 独立拖动会增加手势和窗口状态协调成本。

MVP 当前更需要验证 presence 和亲密关系在场感是否成立，而不是验证多窗口桌面编排能力。

## 决策

MVP 采用**单窗口动态多 pet 渲染**：

- 应用只维护一个透明置顶 pet 主窗口。
- 自己的 pet 常驻在该窗口内。
- 房间内在线远程成员上线时，前端根据 presence 状态在同一窗口内创建远程 pet DOM 节点，并调整主窗口尺寸，为新 pet 分配横向槽位。
- 远程成员离线时，其 pet 在同一窗口内退场，随后移除 DOM 节点并收缩窗口。
- Rust 主进程保持薄层，只负责主透明窗口、置顶、点击穿透、托盘和必要的原生光标采样。
- 前端 webview 负责 presence 订阅、在线成员集合、DOM 布局、动画、消息气泡和像素级命中测试。
- 左键 pet 立即触发原生窗口拖动；点击/长按表情切换不再作为主交互入口，改由右键原生菜单承载后续动作。

前端触发流程：

```text
presence 订阅回调（成员上线/离线）
  → 前端计算在线远程成员列表
  → 前端增删同一窗口内的 pet DOM 节点
  → 前端调用 Tauri window.setSize 调整主窗口尺寸
  → 前端播放到达/退场动画
```

## 后果

**正面：**

- 显著减少 Tauri/Rust 窗口管理代码，不再维护动态 pet 子窗口生命周期。
- 点击穿透、像素级命中测试和原生光标采样只需要服务一个窗口，状态更容易稳定。
- 左键拖动可以统一交给主窗口的原生 `startDragging()`，降低拖动不稳定风险。
- presence 渲染、布局和动画全部集中在前端 DOM 中，符合 ADR-0004 的“前端 webview 承担业务逻辑”原则。
- 更适合 MVP 验证：优先保证“对方出现了”的在场感，而不是先追求每只 pet 独立窗口编排。

**负面：**

- 所有 pet 共享一个窗口边界，远程 pet 不能真正独立分散到桌面任意位置。
- 当成员数量增加时，主窗口会横向变宽；v1 需要限制房间成员规模或采用简单布局策略。
- 单个窗口的点击穿透是整体窗口级能力，虽然前端可以做像素级命中测试，但不能像多窗口那样在 OS 层完全隔离每只 pet。
- 将来如果要支持每只 pet 独立拖拽、独立停靠或跨屏分布，可能需要重新引入多窗口或 canvas/多层窗口方案。

**约束：**

- v1 房间规模仍按小圈子设计，通常 2-6 人。
- 单窗口内布局优先使用简单、稳定的横向槽位，不在 MVP 阶段实现复杂避让。
- 到达动画和退场动画仍是 presence 体验的一部分，不因单窗口方案取消。
- 点击穿透必须继续保证透明区域不阻挡用户操作桌面。
