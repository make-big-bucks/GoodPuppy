# GoodPuppy 会客厅固定宽屏重设计

> 状态：草案 / 待评审
> 日期：2026-06-14
> 范围：会客厅窗口的信息架构、固定宽屏布局、房间详情交互、邀请制入口、成员展示与后续登录合并边界。

## 1. 背景

当前会客厅采用「顶部 header 横跨全宽 + 下方左右分栏」：

- 顶部 header 展示用户信息与复制按钮。
- 左侧 sidebar 展示房间列表、邀请请求、创建房间与加入房间按钮。
- 右侧 main 展示选中房间的成员、简介、进入房间、复制邀请码与邀请成员。

这个结构在功能上可用，但信息层级不够清晰。用户身份、`gp_` 短 ID、房间列表、待处理邀请都属于「导航与账户上下文」，却被拆散在顶部和左侧；右侧详情又混合了房间详情、邀请码、成员邀请等多个入口。

本次设计将会客厅定义为一个固定宽屏桌面管理窗口，而不是手机式响应式页面。窗口主要用于桌面端账户与房间管理，不需要同时维护宽屏与窄屏两套交互模型。

## 2. 目标

1. 将会客厅重构为固定宽屏 master-detail 布局：左侧账户与房间导航，右侧当前房间详情。
2. 移除独立顶部 header，让用户信息固定归属左侧栏。
3. 成员列表展示真实用户信息：Pet 头像、用户名、在线/离线状态。
4. 房间以邀请制为主：去掉显眼的「加入房间」入口，成员在房间详情中按 `gp_` 开头的 GoodPuppy 短 ID 邀请其他成员。
5. 支持用户可见信息编辑：用户名、房间名、房间简介。
6. 为后续设置窗口、Pet 形象管理、登录合并预留自然入口，但不在本阶段实现完整功能。

## 3. 非目标

- 不做窄屏 master-detail 响应式导航。
- 不把会客厅设计成移动端页面。
- 不在第一阶段合并登录页。
- 不在第一阶段删除所有邀请码/RPC 能力；可以先从 UI 主路径隐藏。
- 不实现完整 Pet 形象管理或用户上传 Pet。
- 不重构 Supabase Auth、RLS 或 Tauri 多窗口架构，除非字段缺失导致房间编辑无法落地。

## 4. 布局决策

会客厅采用固定宽屏双栏：

```text
+-------------------------------+----------------------------------------+
| 左侧栏                         | 右侧详情                               |
|                               |                                        |
| 当前用户信息                    | 房间标题 / 简介 / 编辑                 |
| Pet 头像 + 用户名 + ID          |                                        |
| 编辑用户名 icon + ID 复制 icon   | 成员列表 + 邀请 icon                   |
|                               | Pet 头像 + 用户名 + 在线状态           |
| 我的房间                        |                                        |
| 房间列表                        | 输入 `gp_` 短 ID 邀请成员              |
| 待处理邀请                      |                                        |
|                               |                                        |
| 创建房间                        | 进入/退出房间                          |
+-------------------------------+----------------------------------------+
```

建议窗口最小尺寸由 Tauri 限制在约 `1040x680` 或更高。CSS 可以继续使用弹性尺寸，但设计不承诺低于最小宽度后的窄屏体验。

### 为什么不做响应式

当前产品运行环境是桌面端透明宠物应用，会客厅更接近桌面控制面板。完整响应式会引入额外状态：

- 列表页与详情页切换；
- 返回按钮；
- 选中房间后的页面栈；
- 登录 dialog、设置页、头像编辑页在窄屏下的差异交互；
- 两套布局测试面。

这些复杂度对当前核心体验收益有限。后续如果确实需要小窗口模式，应作为独立设计，而不是在本阶段顺手加入。

## 5. 左侧栏设计

### 用户信息区

展示：

- 当前用户 Pet 的 idle 动画头像；
- 用户名；
- `gp_` 开头的 GoodPuppy 短 ID；
- 用户名旁边的小编辑 icon button；
- ID 后的小复制 icon button；
- 设置 icon button。

交互：

- 点击用户名旁边的编辑 icon 打开编辑用户名 modal。
- 点击 ID 旁边的复制 icon 复制 GoodPuppy 短 ID，并短暂显示成功状态。
- 点击设置 icon 进入后续设置窗口或预留入口。
- 点击头像未来用于 Pet 形象管理；第一阶段可不绑定行为，或只打开占位提示。

头像来源：

- 使用当前用户 profile 中的 `pet_id` 与 `skin`。
- 头像应尽量复用宠物动画资源解析逻辑，显示 idle 动画。
- 若 pet 资源加载失败，fallback 到静态占位头像，不影响会客厅主要功能。

### 房间列表

列表项展示：

- 房间名；
- 成员数；
- 选中态。

房间列表仍由当前用户所属 `room_members` 查询得出。选中房间后，右侧详情刷新；固定宽屏下不需要页面跳转。

### 待处理邀请

待处理邀请显示在「我的房间」列表下面，作为左侧栏中的次级区域。

展示：

- 发起人用户名，fallback 到 `gp_id`；
- 发起人 Pet 头像；
- 接受 / 拒绝按钮。

## 6. 右侧房间详情设计

### 房间标题与简介

展示：

- 房间名；
- 房间简介；
- 编辑入口。

权限：

- 所有房间成员都可以编辑房间名和简介。
- 不按房主限制编辑权限。

数据：

- 房间名使用 `rooms.room_name`。
- 房间简介建议新增 `rooms.description`。
- 如果真实 Supabase schema 中缺少 `room_name` 或 `description`，实现时需要补数据库迁移并更新 `docs/database.md`。

### 成员列表

每个成员展示：

- 对应成员当前 Pet 的 idle 动画头像；
- `display_name`，为空时 fallback 到 `gp_id`；
- 在线 / 离线状态标签；
- 当前用户可额外显示「你」标识。

排序：

- 当前用户固定显示在成员列表最上面。
- 其他成员按加入时间或用户名稳定排序，避免刷新后列表跳动。

在线状态来源：

- 第一阶段可以在加载房间数据时查询 `presence` 表。
- 后续可订阅当前房间 presence/realtime 变化，让在线状态实时刷新。
- 如果没有 presence 行，默认显示离线。

### 邀请成员

房间详情中提供邀请成员入口。入口位置在成员列表标题或成员列表右侧，使用小的加号 icon button。

- 成员点击加号 icon 后输入对方 `gp_` 开头的 GoodPuppy 短 ID；
- 系统查找 `profiles.gp_id`；
- 找到后写入 `connection_requests`，状态为 `pending`；
- 对方接受后再加入房间。

创建房间时也可以填写初始成员的 `gp_` 短 ID。语义应是「创建房间后向这些用户发送邀请」，不是直接把对方加入房间。

### 进入房间

房间操作按钮根据当前桌宠所在房间变化：

- 如果当前桌宠不在右侧选中的房间，显示「进入房间」。
- 如果当前桌宠已经在右侧选中的房间，显示「退出房间」。

点击「进入房间」后隐藏会客厅窗口，并通过现有事件切换当前桌宠房间。点击「退出房间」后应让桌宠离开当前房间并回到未进入房间的本地状态；具体事件名与状态流在实施计划中确定。

## 7. 邀请制与邀请码处理

产品主路径改为邀请制：

- 去掉左侧「加入房间」按钮。
- 去掉右侧显眼的「复制邀请码」按钮。
- 成员通过输入用户 `gp_` 开头的 GoodPuppy 短 ID 邀请成员。

实现层面不要求立即删除 `join_room_by_invite` RPC 或 `invite_code` 字段。它们可以暂时保留为兼容能力，避免一次改动牵动数据库与历史流程。文档和 UI 应明确：普通用户主流程是被邀请，而不是拿邀请码主动加入。

## 8. 登录合并边界

登录合并是合理方向，但不纳入第一阶段。

未来目标：

- 会客厅窗口支持未登录态；
- 未登录时左侧用户区显示「未登录」；
- 点击登录打开内置 dialog；
- 登录成功后关闭 dialog，并刷新 profile、房间、邀请数据；
- 独立 `windows/login.html` 保留一段时间作为 fallback，稳定后再考虑删除。

不放进第一阶段的原因：

- 会影响 app 启动与窗口职责；
- 会牵动 `windows/login.html`、`src/windows/login/*`、`src/windows/lounge/lounge-main.js` 与 Tauri 窗口打开流程；
- 与会客厅布局重排可以解耦。

## 9. 前端结构影响

建议继续沿用当前原生 ES modules 与局部 view 模块风格。

保留：

- `src/windows/lounge/lounge.js`：会客厅状态、数据加载、事件绑定。
- `src/windows/lounge/views/room-list.js`：房间列表与待处理邀请渲染。
- `src/windows/lounge/views/room-detail.js`：房间详情与成员渲染。

建议新增或抽出：

- `src/windows/lounge/views/profile-card.js`：左侧当前用户信息区渲染。
- `src/windows/lounge/views/pet-avatar.js`：根据 `pet_id` / `skin` 渲染 Pet idle 头像。

这样可以避免 Pet 头像、用户名 fallback、复制按钮状态等逻辑散落在多个 view 中。

按钮状态还需要知道当前桌宠 active room：

- `lounge-main.js` 应在打开会客厅时获得或请求当前 active room id。
- `lounge.js` 将 active room id 传给 `renderRoomDetail()`。
- `room-detail.js` 根据 `selectedRoom.id === activeRoomId` 渲染「进入房间」或「退出房间」。

## 10. 数据加载影响

`loadPanelData()` 需要扩展加载范围。

当前用户 profile：

```text
profiles:
  id
  gp_id
  display_name
  pet_id
  skin
```

我的房间：

```text
room_members:
  room_id
  rooms:
    id
    room_name
    description
    created_by
```

房间成员：

```text
room_members:
  room_id
  user_id
  profiles:
    id
    gp_id
    display_name
    pet_id
    skin
```

房间在线状态：

```text
presence:
  room_id
  user_id
  is_online
  last_seen
```

待处理邀请：

```text
connection_requests:
  id
  from_id
  profiles:
    id
    gp_id
    display_name
    pet_id
    skin
```

渲染前应在前端将成员 profile 与 presence 合并，形成面向视图的 member view model。

## 11. 数据库与文档影响

需要确认真实数据库 schema 是否已经包含：

- `rooms.room_name`
- `rooms.description`
- `profiles.skin`

实现前应优先使用 Supabase connector 查看真实数据表、字段、RLS policy 和 RPC，而不是只依赖本地 `docs/database.md`。

如果缺失：

- 新增字段需要数据库迁移；
- 更新 `docs/database.md`；
- 如果涉及重大行为或架构取舍，再新增 ADR。

邀请制主路径变化也需要在 `docs/database.md` 中调整说明：邀请码能力可以作为兼容字段保留，但用户主流程不再强调「按邀请码加入房间」。

## 12. 阶段划分

### 阶段 1：会客厅固定宽屏改版

- 去掉顶部 header。
- 左侧栏整合用户信息、房间列表、待处理邀请、创建房间。
- 右侧重构房间详情。
- 成员显示用户名、Pet 头像、在线状态。
- 去掉「加入房间」主入口。
- 房间名与简介支持所有成员编辑。
- 进入/退出按钮根据当前 active room 切换。
- 按需补数据库字段与文档。

### 阶段 2：账户与设置入口

- 用户名编辑体验打磨。
- 设置 icon 打开设置窗口或设置 modal。
- 头像点击进入 Pet 形象管理入口。
- Pet idle 头像资源加载失败时的 fallback 完善。

### 阶段 3：登录合并

- 会客厅支持未登录态。
- 登录表单内嵌 dialog。
- 登录成功刷新会客厅数据。
- 独立登录窗口保留 fallback，确认稳定后再移除。

## 13. 验收标准

第一阶段完成时应满足：

- 会客厅窗口为固定宽屏双栏布局，无独立顶部 header。
- 用户信息区位于左侧栏，用户名旁边有编辑 icon，`gp_` 开头的 GoodPuppy 短 ID 旁边有复制 icon。
- 待处理邀请显示在「我的房间」下面。
- 房间列表选中后，右侧显示对应房间详情。
- 当前用户在成员列表中固定排在最上面。
- 成员列表显示用户名、Pet 头像和在线/离线状态。
- 左侧不再显示「加入房间」按钮。
- 成员列表右侧有加号 icon，可通过 `gp_` 开头的 GoodPuppy 短 ID 邀请成员。
- 所有房间成员可编辑房间名和简介。
- 选中的房间不是当前 active room 时显示「进入房间」；选中的房间是当前 active room 时显示「退出房间」。
- `npm run test` 通过。
- UI 或构建相关改动后，`npm run build` 通过。

## 14. 风险与缓解

### Pet 头像资源复杂度

成员头像需要加载每个用户的 `pet_id` 与 `skin`。如果直接嵌入完整动画渲染逻辑，可能让 lounge 变重。

缓解：第一版封装 `pet-avatar` 视图，只负责解析 idle 图像路径与 fallback；不要把主桌宠状态机搬进会客厅。

### 数据库字段与代码不一致

当前代码已经查询 `rooms.room_name`，而数据库文档中的 `rooms` 示例未列出该字段。实现前必须以真实 Supabase schema 为准。

缓解：实现时先确认 schema；缺字段则补迁移并更新 `docs/database.md`。

### 邀请制语义与旧邀请码能力冲突

如果 UI 移除邀请码入口，但数据库和 RPC 仍保留邀请码，文档可能出现行为不一致。

缓解：将邀请码标注为兼容能力或内部字段，用户主路径描述为 `gp_` 短 ID 邀请。

### 一次合并登录导致范围膨胀

登录合并会牵动窗口生命周期和 auth 初始化，容易和布局重构互相干扰。

缓解：第一阶段不合并登录页。等会客厅布局稳定后，再单独设计和实现未登录态。
